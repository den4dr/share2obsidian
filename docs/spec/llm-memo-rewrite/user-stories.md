## エピック1: 本文のLLMリライト（Must Have）

### ストーリー 1.1: 本文をLLMで書き換える 🔵

**信頼性**: 🔵 *ヒアリングQ2・Q7・Q24より*

**私は** メモを編集中のユーザー **として**
**編集画面の「メモを更改」ボタンを押して、共有直後の元コンテンツをLLMで書き換えたい**
**そうすることで** 手作業での推敲なしに、テンプレートで意図した形（要約・校正など）に本文を整えられる

**関連要件**: REQ-001, REQ-002, REQ-003, REQ-406

**詳細シナリオ**:
1. ユーザーは共有されたテキストをEditScreenで編集している
2. テンプレートに本文用LLMプロンプトが設定されている
3. ユーザーが「メモを更改」ボタンを押す
4. システムはローディング表示を行い、共有/取得直後の元コンテンツ（ProcessedContent。EditScreen上の編集済みbodyではない）とテンプレートのプロンプトをLLM APIへ送信する
5. LLMからの応答テキストで本文フィールドが即時上書きされる

**前提条件**:
- SettingsScreenでLLM APIエンドポイントURL・APIキー・モデル名が設定済みである
- テンプレートに本文用LLMプロンプトが設定されている（未設定の場合はボタンが非活性化される）

**制約事項**:
- 上書き後、元の本文には戻せない（Undo機能はスコープ外）
- 文字数上限・APIコスト対策は行わない
- 元コンテンツが空文字であっても、ボタンは非活性化されず空のままLLMへ送信される

**優先度**: Must Have

---

### ストーリー 1.2: LLM処理中はローディングが表示される 🔵

**信頼性**: 🔵 *ヒアリングQ10より*

**私は** 「メモを更改」を実行したユーザー **として**
**処理中であることが画面上でわかるようにしたい**
**そうすることで** 応答がないまま操作に迷うことがなくなる

**関連要件**: REQ-201, NFR-202

**詳細シナリオ**:
1. ユーザーが「メモを更改」ボタンを押す
2. システムはローディング表示を行う
3. 30秒以内にLLMから応答があれば本文が更新され、ローディングが解除される
4. 30秒を超えた場合は自動的にキャンセルされエラー表示に切り替わる

**前提条件**:
- なし（機能実行の副次動作）

**優先度**: Must Have

---

### ストーリー 1.3: LLM処理が失敗した場合にエラーが通知される 🔵

**信頼性**: 🔵 *ヒアリングQ6より*

**私は** 「メモを更改」を実行したユーザー **として**
**ネットワークエラーやAPIキー不正、タイムアウト時にその旨を知りたい**
**そうすることで** 何が起きたか分からないまま放置されることがなくなる

**関連要件**: NFR-201, EDGE-001, EDGE-002, EDGE-003

**詳細シナリオ**:
1. ユーザーが「メモを更改」ボタンを押す
2. ネットワーク未接続／APIキー不正／タイムアウトのいずれかが発生する
3. システムは既存のToastパターンに沿った日本語エラーメッセージを表示する
4. 本文フィールドは変更されず、編集を継続できる

**前提条件**:
- なし

**優先度**: Must Have

## エピック2: タグ提案（Should Have）

### ストーリー 2.1: 元コンテンツからタグ候補を提案してもらう 🔵

**信頼性**: 🔵 *ヒアリングQ13・Q17・Q18・Q24より*

**私は** メモにタグを付けたいユーザー **として**
**共有/取得直後の元コンテンツから適切なタグをLLMに提案してほしい**
**そうすることで** タグ付けの手間を減らし、タグの一貫性を高められる**

**関連要件**: REQ-103, REQ-301, REQ-302, REQ-406

**詳細シナリオ**:
1. ユーザーがEditScreenを開いている（共有/取得直後の元コンテンツが保持されている）
2. タグ編集エリアの「タグを提案」ボタンを押す
3. システムは共有/取得直後の元コンテンツ（ProcessedContent、本文リライトと同一の入力ソース）を入力としてLLMにタグ候補を生成させる
4. 生成されたタグ候補が既存のタグ入力欄に追加される（既存タグの置換ではない）

**前提条件**:
- SettingsScreenでLLM API設定が完了している

**優先度**: Should Have

## エピック3: カスタムフィールドのLLM生成（Could Have）

### ストーリー 3.1: テンプレート編集時にカスタムフィールドの値取得方法としてLLMを選ぶ 🔵

**信頼性**: 🔵 *ヒアリングQ13・Q15より*

**私は** テンプレートを設計するユーザー **として**
**カスタムフィールドの値取得方法として「LLM生成」を選び、フィールドごとにプロンプトを設定したい**
**そうすることで** 固定値やHTMLメタ情報だけでなく、LLMによる動的な値生成をテンプレートに組み込める**

**関連要件**: REQ-104, REQ-303, REQ-304

**詳細シナリオ**:
1. ユーザーがテンプレート編集画面でカスタムフィールドを追加する
2. 値取得方法（FieldValueSource）の選択肢から「LLM」を選ぶ
3. システムはそのフィールド用のプロンプト入力欄を表示する
4. ユーザーがプロンプトを入力し保存する

**前提条件**:
- テンプレート編集画面（TemplateEditScreen/FieldAddDialog）へのUI変更が許容されている（REQ-405）

**優先度**: Could Have

**備考**: 値生成のタイミング（テンプレート適用時か、EditScreen上のボタン押下時か）はヒアリングで確認できておらず、REQ-304は🟡（黄信号）。設計フェーズで確定が必要。
