# LLMによるメモ更改機能の追加 要件定義書

## 概要

共有・編集中のメモ内容（本文・タグ・カスタムフィールド）を、ユーザーが設定した外部LLM API（OpenAI互換 Chat Completions形式）を用いて書き換える機能を追加する。プロンプトはテンプレート単位でフィールドごとに保存し、ユーザーはEditScreen上のボタン押下でリライトを実行する。本文（body）のリライトを本リリースのMust Have、タグ提案をShould Have、カスタムフィールドのLLM生成をCould Haveと位置付ける。

## 機能要件（EARS記法）

**【信頼性レベル凡例】**:
- 🔵 **青信号**: ユーザヒアリングを参考にした確実な要件
- 🟡 **黄信号**: ユーザヒアリング・既存実装から妥当な推測による要件
- 🔴 **赤信号**: ヒアリングにない推測による要件（設計着手前に要確認）

### 通常要件

- REQ-001: システムは EditScreen の本文編集エリアに「メモを更改」ボタンを表示しなければならない 🔵 *ヒアリングQ2（発動方法）より*
- REQ-002: システムは「メモを更改」ボタン押下時、設定済みのLLM API（OpenAI互換 Chat Completions形式）に、共有/取得直後の元コンテンツ（`ProcessedContent`、テンプレート適用前・ユーザー編集前のテキスト）と、テンプレートに保存された本文用プロンプトを送信しなければならない 🔵 *ヒアリング追加確認（本文入力ソースの明確化）より。当初はEditScreen上の編集済み本文を入力とする案だったが、ユーザーからの指摘により元コンテンツを入力とする方針に修正*
- REQ-003: システムはLLM APIからの応答テキストで、EditScreenの本文フィールドの内容を即時上書きしなければならない 🔵 *ヒアリングQ7（即時上書き）より*
- REQ-004: システムは SettingsScreen に、LLM APIエンドポイントURL・APIキー・モデル名を入力する項目を提供しなければならない 🔵 *ヒアリングQ1・Q8より*

### 条件付き要件

- REQ-101: テンプレートに本文用LLMプロンプトが設定されている場合、システムはそのプロンプトをLLMリクエストに含めなければならない 🔵 *ヒアリングQ14より*
- REQ-102: テンプレートに本文用LLMプロンプトが設定されていない場合、システムは「メモを更改」ボタンを表示するが非活性化（グレーアウト）しなければならない 🔵 *ヒアリング追加確認より*
- REQ-103: タグ提案（Should Have）が有効な場合、システムはタグ編集エリアに「タグを提案」ボタンを表示しなければならない 🔵 *ヒアリングQ13・Q17より*
- REQ-104: カスタムフィールドのLLM生成（Could Have）が有効な場合、システムはテンプレート編集画面で当該フィールド用のプロンプト入力欄を表示しなければならない 🔵 *ヒアリングQ13・Q15より*

### 状態要件

- REQ-201: LLM呼び出し中の状態にある場合、システムはローディング表示を行わなければならない 🔵 *ヒアリングQ10より*
- REQ-202: LLM呼び出し開始から30秒が経過した状態になった場合、システムは自動的にリクエストをキャンセルし、エラーとして扱わなければならない 🔵 *ヒアリングQ10より*

### オプション要件

- REQ-301: システムはタグ編集エリアに「タグを提案」ボタンを表示してもよい（Should Have） 🔵 *ヒアリングQ18（優先順位）より*
- REQ-302: 「タグを提案」ボタン押下時、システムは共有/取得直後の元コンテンツ（`ProcessedContent`、REQ-002と同一の入力ソース）を入力としてLLMにタグ候補を生成させ、生成結果を既存のタグ入力欄に追加してもよい 🔵 *ヒアリング追加確認（入力ソースの統一）より*
- REQ-303: システムはカスタムフィールドの値取得方法（`FieldValueSource`）に `LLM` を追加してもよい（Could Have） 🔵 *ヒアリングQ15・Q18より*
- REQ-304: `FieldValueSource` が `LLM` に設定されたカスタムフィールドについて、システムはテンプレート適用時にLLMで値を生成してもよい 🟡 *Q13・Q15から妥当な推測。生成タイミング（テンプレート適用時 or EditScreen上のボタン押下時）は未確認*

### 制約要件

- REQ-401: システムはLLM APIキーを暗号化されたストレージに保存しなければならない（平文DataStoreへの保存は禁止） 🔵 *ヒアリングQ4より*
- REQ-402: システムはLLM APIへのリクエストをOpenAI互換のChat Completions形式で送信しなければならない 🔵 *ヒアリングQ5より*
- REQ-403: システムは本文の文字数上限チェックやAPIコスト対策を行わなくてよい（本リリース時点でスコープ外） 🔵 *ヒアリングQ11より*
- REQ-404: システムはSettings画面でのAPI接続情報の事前検証（接続テスト）を行わなくてよい 🔵 *ヒアリングQ12より*
- REQ-405: 本機能追加に伴い、既存の `TemplateEditScreen` / `FieldAddDialog` のUIを変更してもよい 🔵 *ヒアリングQ19より*
- REQ-406: システムはLLM入力用に、EditScreen表示後も共有/取得直後の元コンテンツ（`ProcessedContent`）をテンプレート適用・ユーザー編集とは独立して保持し続けなければならない 🟡 *REQ-002/REQ-302を実現するための技術的帰結。直接ヒアリングはしていないが要件から論理的に導出される制約*

## 非機能要件

### パフォーマンス

- NFR-001: LLM呼び出しのタイムアウトは30秒とする 🔵 *ヒアリングQ10より*

### セキュリティ

- NFR-101: LLM APIキーは暗号化ストレージ（例: EncryptedSharedPreferences等）に保存しなければならない 🔵 *ヒアリングQ4より*
- NFR-102: システムはLLM APIキー等の機微情報をログ・クラッシュレポートに出力してはならない 🔵 *ヒアリング追加確認より*

### ユーザビリティ

- NFR-201: LLM処理が失敗した場合、システムは既存の日本語Toastエラーパターン（`ActivityNotFoundException`と同様の扱い）に沿ったメッセージを表示しなければならない 🔵 *ヒアリングQ6より*
- NFR-202: LLM処理中、システムはローディング表示によりユーザーに処理中であることを明示しなければならない 🔵 *ヒアリングQ10より*

## Edgeケース

### エラー処理

- EDGE-001: ネットワーク接続がない状態でLLM呼び出しが行われた場合、システムはToastで日本語エラーメッセージを表示し、本文を変更してはならない 🔵 *ヒアリングQ6より*
- EDGE-002: APIキーが不正、またはLLM APIが認証エラーを返した場合、システムはToastで日本語エラーメッセージを表示しなければならない 🔵 *ヒアリングQ6より*
- EDGE-003: LLM API呼び出しが30秒でタイムアウトした場合、システムはリクエストをキャンセルし、Toastでエラーメッセージを表示しなければならない 🔵 *ヒアリングQ10より*
- EDGE-004: LLM APIが空文字列またはエラーレスポンスを返した場合、システムは本文を上書きせず、Toastでエラーメッセージを表示しなければならない 🟡 *既存のエラー処理方針から妥当な推測。空応答時の扱いは直接確認していない*

### 境界値

- EDGE-101: LLM入力ソース（`ProcessedContent`）が空文字であっても、システムは「メモを更改」「タグを提案」ボタンを非活性化してはならず、空文字のままLLM APIへ送信しなければならない（応答内容はプロンプト次第） 🔵 *ヒアリング追加確認より*
